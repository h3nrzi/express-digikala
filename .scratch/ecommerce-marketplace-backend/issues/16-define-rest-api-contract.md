# تعیین منابع و قرارداد REST API

## Question

APIهای نسخه اول چه مرزهای منبع و عملیاتی دارند و قراردادهای مشترک برای نسخه‌بندی، خطاها، صفحه‌بندی، اعتبارسنجی، idempotency و دسترسی چگونه تعریف می‌شود؟ قرارداد باید جریان‌های مشتری، فروشنده و ادمین را پوشش دهد و با مدل معماری و قواعد کسب‌وکار سازگار باشد.

## Answer

کاربر هر شش پیشنهاد را تأیید کرد. قرارداد نسخهٔ اول بر این مبنا شکل می‌گیرد:

1. **مرز API و منابع:** API زیر `/api/v1` عرضه می‌شود و مسیرهای عملیات داخلی زیر `/api/v1/admin` قرار می‌گیرند. خواندن کاتالوگ و خانواده/گونهٔ کالا و پیشنهادهای منتشرشده عمومی است. منابع خریدار شامل حساب و نشانی‌های خودش، سبد، checkout، سفارش‌های خودش، لغو، مرجوعی و پرونده‌های پشتیبانی است: خریدار سبد را می‌خواند و تغییر می‌دهد، checkout می‌کند، سفارش‌های خودش را می‌بیند، پیش از تحویل به حمل درخواست لغو می‌دهد، پس از تحویل درخواست مرجوعی ثبت می‌کند و پروندهٔ پشتیبانی را پیگیری می‌کند. API داخلی عملیات مشارکت فروشنده، کاتالوگ، پیشنهاد و موجودی، سفارش و ارسال، پرداخت و تسویه، تصمیم مرجوعی و پشتیبانی را پوشش می‌دهد. فروشندگان ثالث در MVP حساب ورود یا API ندارند؛ رویدادهای ارائه‌دهندهٔ پرداخت از مسیر webhook جدا دریافت می‌شوند. رفتار checkout، سفارش و پرداخت از [تعیین مرز سبد خرید و چرخه سفارش چندفروشنده‌ای](08-define-cart-and-order-lifecycle.md) و [تعیین چرخه پرداخت، بازپرداخت و تسویه فروشنده](11-define-payment-and-settlement.md) پیروی می‌کند.
2. **نسخه و قالب:** بدنه‌ها JSON با UTF-8 هستند. قرارداد از متدها و کدهای وضعیت متعارف HTTP استفاده می‌کند؛ تغییر ناسازگار در نسخهٔ مسیر تازه عرضه می‌شود.
3. **اعتبارسنجی و خطا:** پاسخ خطا قالب مشترک دارد: کد ماشینی پایدار، پیام فارسی، شناسهٔ پیگیری، و برای ورودی نامعتبر جزئیات خطا به تفکیک فیلد. اعتبارسنجی پیش از هر تغییر وضعیت انجام می‌شود و کد HTTP نوع خطا را بازتاب می‌دهد.
4. **فهرست‌ها:** فهرست کاتالوگ و عملیات از cursor pagination با `limit` دارای سقف، `cursor` و `nextCursor` استفاده می‌کند. فیلتر و مرتب‌سازی فقط از گزینه‌های مجاز هر منبع می‌پذیرد.
5. **تکرار امن:** فرمان‌های اثرگذار بر موجودی یا پول، از جمله checkout، آغاز پرداخت، لغو، درخواست مرجوعی، بازپرداخت و تسویه، ارسال `Idempotency-Key` برایشان الزامی است. تکرار همان درخواست همان نتیجه را می‌دهد؛ استفادهٔ دوباره از کلید با محتوای متفاوت تعارض است. webhookها با شناسهٔ رویداد ارائه‌دهنده deduplicate می‌شوند.
6. **احراز هویت و مجوز:** API خریدار پس از ورود با OTP شمارهٔ تأییدشده و صدور Bearer token کوتاه‌عمر در دسترس است و هر خریدار فقط به داده‌های خودش دسترسی دارد. API داخلی به حساب فردی، عامل دوم و نقش عملیاتی متناسب نیاز دارد؛ دسترسی نقش‌ها از تصمیم [تعیین عملیات ادمین و پشتیبانی](13-define-operations-and-support.md) پیروی می‌کند.
